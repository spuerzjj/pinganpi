# 平安批手机号账号系统设计

## 背景

阶段 16B 已经实现 CloudBase 同步代理，但当前同步身份仍依赖手工配置的 `householdId + memberId + token`。这能用于开发和烟测，但不能解决真实用户问题：App 卸载、换机或本地数据损坏后，用户需要重新找回自己的信件、钱匣、账本和档案。

因此账号系统应独立成阶段 17，先解决“这个使用者是谁、重装后能否找回身份”，再在阶段 18 处理“这两个人如何组成一对、同步时如何按账号关系授权”。

## 决策

阶段 17 采用 **CloudBase 手机号验证码登录 + 平安批最小账号档案**。

需要账号系统，但不是完整社交账号系统：

- 需要：手机号验证码登录、CloudBase UID、登录态恢复、UID 到平安批账号的映射。
- 不需要：密码、昵称头像资料页、好友系统、联系人导入、公开注册广场、多账号社交关系。

手机号用于身份恢复、账号展示和后续同步授权。用户已明确接受在平安批账号档案中保存完整手机号；但手机号仍不应被无关复制到信件正文、邮政记录、AI prompt、AI metadata 或业务日志。

## 阶段边界

### 阶段 17：手机号账号系统

目标：用户卸载重装后，可以通过手机号重新登录，并恢复同一个平安批账号身份。

包含：

- CloudBase 手机号验证码登录接入。
- App 启动时恢复 CloudBase 登录态。
- 建立 `PinganpiAccount`：把 CloudBase UID 映射到平安批账号。
- 本地保存账号登录状态摘要和账号展示所需手机号；不保存短信验证码或 CloudBase 管理密钥。
- 登录后能读取账号档案，判断后续应进入“创建关系 / 加入关系 / 已有关系恢复”流程。
- 登出或登录态失效时，停止云同步，只允许本地只读或重新登录。

不包含：

- 创建 household / pair。
- 邀请另一方。
- 创建 household / pair。
- 邀请另一方。
- 把 `sync-proxy` 改为基于登录账号和双人关系的正式同步授权。

这些留到阶段 18。

### 阶段 18：双人绑定与同步授权

目标：在已有手机号账号身份基础上，建立一对通信关系，并让同步代理按登录账号所属关系授权访问。

包含：

- 创建 household / pair。
- 生成 24 小时有效、一次性的邀请码。
- 另一方手机号登录后输入邀请码即加入第二个成员席位，不需要创建方二次确认。
- 一个手机号账号同一时间只能属于一个有效双人关系。
- `sync-proxy` 从手工 `PINGANPI_SYNC_MEMBER_TOKENS` 迁移到 CloudBase 登录态 + 账号 / 关系 / 成员数据库授权。
- 第一版不做独立设备授权、设备 token 签发、设备 token 轮换或设备撤销；`deviceId` 只用于本地实例区分、同步冲突标记和调试。

## 数据模型

阶段 17 新增最小账号集合，建议命名为 `pinganpi_accounts`。

```ts
interface PinganpiAccount {
  accountId: string;
  authUid: string;
  phoneNumber: string | null;
  status: "active" | "disabled";
  createdAtIso: string;
  lastLoginAtIso: string;
}
```

说明：

- `authUid` 来自 CloudBase 身份认证，是恢复身份的稳定主键。
- `accountId` 是平安批业务账号 id，避免业务层到处直接依赖云厂商 UID。
- `phoneNumber` 保存完整手机号，用于账号恢复核对和 App 内展示。这是用户确认后的产品取舍。
- household、member、device 授权不放在本阶段模型里，避免账号系统和情侣关系绑定耦合。

## App 流程

### 首次打开

1. App 检查本地 CloudBase 登录态。
2. 未登录时显示手机号验证码登录。
3. 登录成功后调用账号初始化接口。
4. 如果该 UID 没有 `PinganpiAccount`，服务端创建账号档案。
5. App 进入后续引导：创建一对关系或输入邀请码。这个引导的真实实现属于阶段 18。

### 卸载重装

1. 用户重新安装 App。
2. 用同一手机号登录。
3. CloudBase 返回同一 UID 或可关联到同一账号的身份。
4. 服务端按 UID 找回 `PinganpiAccount`。
5. 阶段 18 会继续按账号找回 household / member 授权；阶段 17 只保证账号身份可恢复。

### 登录态失效

1. App 保留本地数据。
2. 云同步暂停。
3. 用户重新手机号登录后，再恢复云端读取。
4. 不允许在未认证状态下投寄或拆阅需要云端校验的操作。

## 服务端边界

阶段 17 新增账号服务边界，建议放在 `server/account-proxy/` 或合并到后续 auth service 中，具体 implementation plan 再确定。

最小接口：

- `GET /account/session`：返回当前登录 UID 对应的平安批账号档案。
- `POST /account/ensure`：登录成功后确保账号档案存在，并更新 `lastLoginAtIso`。

接口必须依赖 CloudBase Auth 的已验证登录身份，不能接受客户端直接传入 `authUid` 作为可信身份。

## 安全与隐私

- 账号档案可保存完整手机号，这是用户确认后的产品决策。
- 不在 Git、AI metadata、信件、邮政记录或无关业务日志中复制完整手机号。
- 短信验证码只用于 CloudBase 登录流程，不进入平安批服务端日志。
- 服务端错误只返回受控短错误，不返回 CloudBase 原始 token、手机号或认证响应。
- 未登录状态不能访问云端同步数据。
- 账号阶段不签发手工同步 token；阶段 18 统一改为登录账号 + 双人关系授权。

## 验收标准

- 用户可用手机号验证码登录。
- 首次登录会创建平安批账号档案。
- 重装或清空本地存储后，用同一手机号可找回同一账号档案。
- 登录态失效后，App 能进入重新登录状态，云同步不会继续使用旧身份。
- 账号档案包含完整手机号，App 可展示当前登录手机号。
- 现有写信、投寄、钱匣、邮政状态机、AI 起稿规则不变。

## 后续衔接

阶段 18 基于 `PinganpiAccount.accountId` 和 CloudBase UID 实现：

- 创建 household。
- 分配两个 member 席位。
- 邀请另一方输入邀请码即加入。
- 限制一个账号只能属于一个有效双人关系。
- 改造 `sync-proxy` 为登录账号和关系成员授权查询。
- 不做独立设备授权；`deviceId` 只作为本地实例和同步调试字段。
