# 平安批写信分步流程设计

## 背景

当前写信页已经接入本地写信服务、模板代书引擎、草稿保存、钱匣扣款、邮政记录和本地持久化，但交互仍集中在一个页面内完成。用户希望写信不要像现代网页表单一样一次性填完，而是拆成多个步骤，贴近“找代笔先生、口述、起稿、校改、算账、封缄”的旧时代寄信过程。

本设计只调整写信页面的交互结构，不改变领域规则和写信服务边界。

## 目标

- 将写信页改为 5 步可回看流程。
- 移动端优先，同时保留 PC 浏览器可用体验。
- 保持旧账簿、代书摊、邮政登记册的克制档案风格。
- 继续复用现有领域层、写信服务和模板代书引擎，不在 UI 中重复实现规则。
- 支持本地 mock / localStorage 状态，后续可继续接云端同步。

## 非目标

- 不在本阶段接 AI 改写。
- 不做现代聊天式输入、消息气泡或实时物流地图。
- 不实现草稿列表、草稿继续编辑和草稿删除。
- 不在本阶段统一修复 toast / snackbar 提示问题；该问题已记录到 UI 修复清单。

## 流程结构

写信页拆为 5 步：

1. **选写法**
   - 用户选择亲笔，或选择今日在摊的代笔先生。
   - 展示先生姓名、风格、代书费和今日是否在摊。
   - 不在摊的先生可以展示，但不能作为可投寄流程的有效选择。

2. **口述**
   - 用户输入给先生听的原始口述。
   - 口述为空时不能进入起稿。
   - 从本步骤开始允许“存作草稿”。

3. **起稿**
   - 调用现有 `createScribeDraft` / 模板代书引擎生成初稿。
   - 选择亲笔时，展示亲笔草稿。
   - 起稿结果写入页面临时状态，并默认填充最终正文。

4. **校改**
   - 用户手工修改最终正文。
   - 后续保存草稿和投寄正文以本步骤的最终正文为准。
   - 最终正文为空时不能进入投寄。

5. **投寄**
   - 展示普通 / 挂号选择。
   - 展示代书费、邮资、总额、钱匣余额、邮路窗口。
   - 余额足够才允许封缄投寄；余额不足时保留草稿状态并展示失败原因。

## 导航规则

- 顶部显示 5 步步骤条。
- 当前步骤高亮。
- 已完成步骤可点击回看和修改。
- 未达到前置条件的后续步骤不可点击。
- 底部操作区在移动端保持稳定位置，包含：
  - `上一步`
  - `存作草稿`
  - `下一步`
  - 最后一步将 `下一步` 替换为 `封缄投寄`
- `存作草稿` 在口述为空时禁用；口述存在后可用。

## 状态规则

页面维护轻量 wizard 状态：

- `currentStep`
- `selectedScribeId`
- `oralText`
- `scribeDraft`
- `finalText`
- `registered`
- `draftDirty`

当用户返回前面步骤并修改写法或口述时：

- 标记 `draftDirty = true`。
- 禁止直接进入校改或投寄。
- 用户需要重新进入起稿步骤生成新初稿。
- 这样避免最终正文和最新口述、最新先生选择不一致。

起稿成功后：

- `scribeDraft` 更新为模板引擎输出。
- 如果 `finalText` 为空，或旧正文来自上一次起稿，则同步填入新草稿。
- `draftDirty = false`。

## 代码边界

UI 页面只负责流程状态和展示，不重复实现业务规则。

继续使用现有服务：

- `createScribeDraft`
- `saveDraftPaper`
- `postLetter`
- `calculateWriteLetterCost`

如实现时需要降低 `WriteLetterPage.vue` 复杂度，可新增：

- `src/app/write-letter-wizard.ts`

该 helper 只处理：

- 步骤定义。
- 步骤是否可进入。
- 当前步骤是否可继续。
- 按钮文案。
- 写法或口述变更后的 dirty 状态。

该 helper 不处理：

- 邮资计算。
- 钱匣扣款。
- 先生出勤规则。
- 时代日期。
- 邮政状态流转。

## 错误处理

- 先生今日不在摊：沿用 `postLetter` 返回原因，阻止投寄。
- 钱匣余额不足：沿用 `postLetter` 返回原因，阻止投寄。
- 口述为空：禁用进入起稿。
- 正文为空：禁用进入投寄。
- 起稿过期：提示需要重新起稿，不能跳到投寄。

本阶段不新增全局 toast 机制，成功 / 失败反馈仍使用当前页面提示方式，后续 UI polish 统一调整。

## 测试与验证

单元测试：

- 为 `write-letter-wizard.ts` 增加 Vitest 覆盖。
- 覆盖步骤可进入条件。
- 覆盖修改口述或写法后需要重新起稿。
- 覆盖存草稿和投寄前的基本可用性判断。

回归测试：

- 保留并通过现有 `write-letter-service`、`scribe-template-engine`、`app-model` 测试。

手工验证：

- 浏览器打开写信页。
- 完成 `选写法 → 口述 → 起稿 → 校改 → 投寄`。
- 回退修改口述后确认需要重新起稿。
- 保存草稿后刷新页面，确认草稿进入本地状态。
- 投寄后确认钱匣扣款、账本追加、档案新增。
- 在 PC 宽屏下确认页面可用，移动端宽度下不出现文字重叠。

常规验证命令：

```bash
npm test
npm run typecheck
npm run build
```
